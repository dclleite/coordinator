# Runtime: inside a T3 Code thread

You are in this runtime when `T3CODE_THREAD_ID` is set and the `t3-code` tools answer.
Rows marked *untested* are read from the tool schemas but were not exercised; do not present them as known behavior.
Trial results are in `docs/trial-plan.md`.

## Where each agent runs

- A delegated task (`delegate_task`) runs only in the launching thread's own project. Passing another project's `target.projectId` is refused; omit it.
- So the coordinator delegates its sub-coordinator and its fast worker into the coordinator's own project, and their end wakes it.
- A sub-coordinator launches workers in other projects as threads (`t3_thread_launch`) and waits on them itself: a launched thread never wakes anyone, `delegatedFrom` included.
- A launched thread does not record a parent in the runtime (`parentThreadId` is null): the tree on the board comes from `agents.tsv`.

## Capability to tool

| Capability | Tool and what matters |
|---|---|
| Providers, models, effort names | `orchestrator_capabilities`, once per thread before the first launch. The instance id and the effort option name of each provider are columns 3 and 4 of `.private/config/providers.tsv`; `dispatch.sh` prints them as `instance` and `effort_option`. |
| Claim the coordinator's thread | `scripts/guard.sh claim`, once per coordinator thread, so the guard knows which session it checks. |
| Launch the sub-coordinator or a fast worker (coordinator) | `delegate_task` with `mode: "async"`, `title`, `task` = the `message=` line, and `target: {providerInstanceId, model, options: {<effort_option>: <effort>}}`. No `projectId`. The thread id for `dispatch.sh launched` is the `childThreadId`. |
| Launch a worker in a repository (sub-coordinator) | `t3_project_list`, then `t3_project_create {title, workspaceRoot}` if missing. `t3_thread_launch` with `projectId`, `title`, `message` = the brief pointer, `modelSelection: {instanceId, model, options}` and `workspaceStrategy: {type: "existing_worktree", worktreePath}` for a worktree made under `<repo>/.claude/worktrees/`. A runtime-made worktree (`type: "worktree"`) lands under the runtime's own folder: record its path all the same. |
| Permission mode | Omit `runtimeMode` to inherit. A child never runs with a broader mode than its launcher, so the coordinator's mode is the ceiling for everyone. Narrower modes pause for the developer's approval: use them only for an agent the developer means to supervise. |
| Wait (sub-coordinator) | `t3_thread_wait` on the worker's thread; on a timeout with `next`, end the turn. Never poll. |
| Learn that an agent finished | A delegated child wakes its launcher when its turn ends. A wake is not always a completion: a child that ends its turn while its own workers run wakes the launcher early. The handoff file is the signal; `scripts/report.sh` reads the inbox. |
| Read an agent | `task_status` for a delegated task; `t3_thread_read` with a small `limit` for any thread. `scripts/live.sh <thread-id>` gives the state in one word. |
| Steer | `t3_thread_send` to the thread id with the new brief pointer. To a running delegated child, `mode: "auto"` steers the running turn. The `t3 thread send` command queues it as the child's next run instead, interrupting nothing; the launcher is woken once, after the last queued run. |
| The developer writes to a sub-coordinator | The thread's `link` (from the launch result, copied as it is) opens it in the app. A message sent to it from outside its parent is accepted and queued. Typing in the app's composer of a delegated thread has not been tried by an agent. Either way the sub-coordinator appends what it receives with `request-add.sh`. |
| A child asks a question | The launcher is notified. `t3_pending_request` reads and answers it; a question that changes what gets built goes to the developer first. |
| Stop | `task_cancel` for a delegated task (it also stops what that child delegated, *untested*); `t3_thread_interrupt` for a launched thread. |
| Show what runs | `scripts/status.sh`, or `scripts/panel.sh start` for the page. `html_preview` then `html_render` draw a snapshot in the thread; such a page cannot fetch from this machine, so the data goes into the HTML. |
| Keep the list readable | Titles as printed by `dispatch.sh` (`<KEY> · <role> · <folder>`). `t3_thread_organize` to pin the coordinator and settle finished threads. |
| Follow a merge request | `watch_pull_request` (takes a `host` for a self-hosted forge), from the worker thread that opened it. A delegated child cannot watch (*untested*). |
| Periodic work with no turn open | `schedule_task`, only when the developer asks. |

## Settings worth turning on

The developer flips these in the app; no tool sets them.

- Settings → General: thread notifications (`notifications`, or with sound) and in-app notifications. Off by default; without them a finished thread that wakes nobody goes unnoticed.
- Settings → Threads: auto-settle after merge (on by default), and fewer days before auto-settle, so finished workers leave the sidebar.
- Settings → Threads, project overrides: turn the personal-account provider off for each company project, so the boundary holds against a mistake.
- Settings → Worktrees: cleanup on merge and after settling, keeping worktrees with uncommitted changes. It reaches only the runtime's own worktree folder; `scripts/worktree-cleanup.sh` stays needed for `<repo>/.claude/worktrees/`.
- Settings → Maintenance: retention days for browser artifacts and logs.
- Optional, by tool: `t3_project_update` gives a project a default model with effort and an icon (*untested*).

## Values

- A link to a thread is the `link` field of a tool result, copied as it is. Never write a thread title or a bare id to the developer.
- `scripts/live.sh` asks `t3 thread show --messages 0 --json <id>`; it prints `unknown` when the command is missing or does not answer.
